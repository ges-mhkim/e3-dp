# 002 기준 장치 패킷 캡처
목표: 구 장치(10.10.0.220)의 실제 통신 프레임을 읽기 전용으로 확보해 시뮬레이터의 기준 데이터로 쓴다.
상태: 진행중

## 사실 (확인된 것만)
- 기준 장치: 10.10.0.220, Ubuntu 16.04.2. 연구소 보관 장치(현장 운영 아님, 사용자 확인 2026-10-26). 접속 정보는 스킬 `e3dp-ref-device`.
- 연구소 장치라 실제 현장 통신(Host 요청, 정상 GW 응답, 정류기)이 거의 없을 수 있음. 캡처는 보조 자료이고 시뮬레이터 기준은 소스(task 001, 005, 006).
- 기준 장치에 tcpdump 없음. python3, root 있음 → raw 소켓(`AF_PACKET`)으로 수신 패킷 읽기 가능.
- 하위 장치 망: eth1 192.168.123.2, GW 192.168.123.11 / .12. 상위 서버: 10.10.0.144.
- 캡처는 장치에 파일을 쓰지 않고 ssh 채널로 PC에 직접 전송하는 방식.

## 캡처 결과 (1차, 2026-10-26 12:47, 300초, 12,845프레임)
- 파일: `tests/fixtures/ref_220/capture_20261026_124719.pcap` (+ `.ifaces`: 프레임별 인터페이스)
- 도구: `tests/tools/capture_ref.py`(캡처), `tests/tools/pcap_summary.py`(집계). 장치에 파일을 쓰지 않음.
- 장치 부하: 캡처 전 load 1.3, 메모리 여유 있음. `nice 19`로 실행.
- DP ↔ Host(UDP/TCP): 300초 동안 0건. 경보·실시간·정시수집은 이벤트 또는 주기가 길어 1차 캡처에 없음.
- DP → GW Modbus TCP 1502: GW 192.168.123.11 / .12, unit ID 1~5, 매 폴링마다 새 TCP 연결.
  - 요청 형식(12바이트): `[txid 2][proto 0000][len 0006][unit 1][func 03][start 0000][count 0078]` → 함수 03, 시작 0, 120 레지스터.
  - txid는 요청마다 증가.
  - unit별 약 95회/300초(약 3.2초 주기).
- GW 응답: 요청 9종(.11 unit 1~5, .12 unit 1~4) 중 응답이 있는 것은 4종(.11 unit 5, .12 unit 2·3·4)이고 모두 12바이트, 함수 코드 0x84. 나머지 5종은 응답 데이터 없음.
  - 정상 응답(249바이트)은 이 캡처에 없음. 정상 응답 형식은 소스에서 확정하고, 정상 응답 캡처는 별도 확보 필요.
  - 소스 확인 결과(task 005): 12바이트 응답은 `rcvLen == MODBUS_RT_REQUEST_SIZE`로 판정되는 "E3-GW에 설정 없음" 응답. DP는 해당 port를 COMM_ALARM으로 표시.
  - 폴링 주기 3.2초는 무응답 5종 × 응답 대기 500ms(poll 타임아웃) + 처리 시간으로 설명됨.
- ICMP: DP ↔ 각 GW ping, 5분에 204회(약 1.5초 주기), 56바이트 페이로드.
- 그 외 UDP: 같은 망의 다른 PC가 보내는 NetBIOS(137/138), 1947, 6000(멀티캐스트), LLMNR(5355). DP 통신과 무관.
- eth0 캡처에 eth1 측 10.10.0.x 브로드캐스트도 보임. 두 인터페이스가 같은 L2에 연결된 구성으로 보임(미확인).
