# 010 함수 정의 표준화 비교표 (K&R → ANSI 프로토타입)

작성일: 2026-11-10. 대상: `e3dp.2.1` 소스(git 서브모듈, 변환 전 HEAD `a10979f`).

## 1. 요약

- 변환한 함수 정의: **138개**, 파일 **43개**. 함수 머리 부분(이름~`{` 직전)만 바꿨고 본문은 바꾸지 않았다.
- 빌드 기준 K&R 경고(`-Wold-style-definition`): **138건 → 0건**. 전체 `.c` 108개 파일 스캔에서도 0건.
- 컴파일 오류: 변환 전후 모두 0건.
- 경고(저장소 기본 옵션 기준, 직접 측정): **514건 → 514건**, 경고 종류·건수 차이 없음. 기본 옵션에는 `-Wold-style-definition`이 없어 K&R 경고가 집계되지 않는다.
- 경고(검증용으로 `-Wold-style-definition`을 추가한 빌드): 652건 → 514건. 줄어든 138건은 모두 K&R 경고이고 그 밖의 경고는 변하지 않았다.
- 오브젝트(`.o`) 108개 비교, K&R 변환만 마친 시점(8단계 끝): **106개 완전 동일**, **2개는 호출 전 `mov $0x0,%eax` 1개 명령만 차이**(3절), 코드가 달라진 오브젝트 **0개**.
- 추가 작업: 빈 괄호 `f()` 선언 15곳과 연관 코드를 수정했다(8절). 함수 포인터 타입 `findVar`, `write_method`가 대상이다.
- 최종 상태 오브젝트 108개 비교: **105개 완전 동일**, **3개는 호출 전 `mov $0x0,%eax` 1개 명령만 차이**(`pdu_tree.o` 추가), 코드가 달라진 오브젝트 **0개**. 경고 514건(변환 전과 같음), 오류 0건.
- **C23 모드(`-std=gnu23`) 빌드**: 변환 전 소스는 오류 1건(`lib/pdu/pdu_tree.c:183`, `too many arguments to function ‘vp->findVar’`)이고, 최종 소스는 오류 0건에 `.o` 108개 모두 생성(8절).
- 전체 소스 스캔(`-Wold-style-definition -Wstrict-prototypes`, `.c` 108개): K&R 정의 0건, 빈 괄호 선언 0건.
- **최신 컴파일러 확인**(9절): gcc 15.3·16.2를 시스템 변경 없이 홈 폴더에 풀어 실제로 빌드했다. 변환 전 원본은 gcc 15.3에서 빌드가 실패하고, 최종 소스는 gcc 15.3·16.2 모두 오류 0건·`.o` 108개이다.
- **`-Wno-error=...` 옵션 뒤에 숨어 있던 오류 38건**(선언 누락 31, 타입 생략 3, 포인터·정수 혼용 3, 함수 포인터 불일치 1)을 모두 고쳤다. 이제 이 옵션을 빼도 gcc 15·16에서 오류가 없다. 경고는 514건에서 401건으로 줄었고 새로 생긴 경고는 없다(x86_64, gcc 14.2 기본 옵션).
- 로직 영향 가능 항목 1건은 동작을 바꾸지 않고 두고 검토를 요청한다(`src/acon_agent/socket.c:192`, 9.5절). `-fcommon`은 아직 필요하다(9.2절).
- 커밋은 하지 않았다. 변경은 서브모듈 작업 트리에 남아 있다. 신규 파일 `include/pdu/pdu_callback.h`는 git이 추적하지 않는 파일이므로 커밋할 때 `git add`가 필요하다.

## 2. 검증 방법

- 환경: Windows의 WSL `Debian`(Debian 13.5, gcc 14.2.0-19, x86_64). 장치(armv7l)가 아니다.
- 기준(변환 전): 변환 전 소스를 WSL 작업 폴더에 복사해 `make clean all`로 빌드한 오브젝트와 빌드 로그. 변환 전 빌드 결과: `BUILD_EXIT=0`, `error:` 0건, `warning:` 652건, `.o` 108개.
- 빌드 방식: 저장소의 실제 Makefile 그대로 사용. `HOME_DIR`, `OPT_DIR`, `BUILD_LOG`를 작업 폴더로 바꾸고 `CC="gcc -Wold-style-definition"`만 추가했다. 소스 폴더의 `bin/`, `web/`, 장치 경로는 건드리지 않았다.
- 대상 목록: 변환 전 빌드 로그의 `old-style function definition` 경고 138건. 모듈별 `-D` 옵션이 실제 빌드와 같다.
- 마지막에 `-Wold-style-definition` 없이 저장소 기본 옵션만으로 변환 전(백업본)·후 소스를 각각 빌드해 경고 건수를 비교했다: 두 빌드 모두 `BUILD_EXIT=0`, `error:` 0건, `warning:` 514건, `.o` 108개, 경고 목록 차이 없음.
- 단계마다: 변환 → 소스 전체를 새 작업 폴더에 복사 → `make clean all` → 변환 전 오브젝트와 비교.
- 오브젝트 비교 기준: `objdump -dr`의 명령 열(주소·재배치 주소 정규화)과 `.rodata`·`.data` 내용. `SAME`은 이 둘이 같은 경우, `PROTO`는 다른 모든 명령이 같고 `call` 바로 앞의 `mov $0x0,%eax`만 빠진 경우, `DIFF`는 그 밖의 차이.
- 변환 전 소스와의 비교에는 git(`git diff`)을 사용했고, 프로젝트 밖에 소스 전체 백업을 두었다(12절).

## 3. K&R 변환에서의 오브젝트 차이 2건 (`PROTO`)

(빈 괄호 선언 수정 후에는 같은 유형의 차이가 `lib/pdu/pdu_tree.o`에서 1건 더 생겨 총 3건이다. 8절 참조.)

`src/acon_agent/acon_parse.o`와 `src/db/ldb_handler.o`. 두 오브젝트 모두 함수 본문이 아니라 **호출하는 쪽**에서 `call` 바로 앞의 `mov $0x0,%eax` 1개 명령이 빠졌다. 그 외 명령은 모두 같다.

- 해당 호출: `acon_parse.c`의 `DrScan__ao_set` 호출(`acon_parse.c:188`, 인자는 상수 `USE_RECT_LPORT_TABLE`), `ldb_handler.c`의 `DrDbmResponseHandler` 호출(`ldb_handler.c:360`, `DrDbmRecvHandler` 안). 둘 다 같은 파일에서 K&R로 정의된 함수를 부르며, 별도의 프로토타입 선언이 보이지 않는 경우이다.
- 원인: K&R 정의는 프로토타입이 아니므로, 프로토타입 선언이 따로 없으면 같은 파일의 호출은 "인자 정보 없는 호출"로 컴파일된다. x86-64에서는 이런 호출 앞에 `%eax`를 0으로 만드는 명령이 붙는다. 정의가 프로토타입이 되면 이 명령이 사라진다.
- 인자 값·개수·타입 변환은 달라지지 않았다(명령 열의 나머지가 동일).
- 이 명령은 x86-64 호출 규약의 특성이다. 장치(armv7l)의 코드 생성은 장치에서 따로 확인해야 한다(11절).

## 6. 변환 중 발견해서 고친 문제

- 변환 도구의 오류 1건: 한 줄이 100자를 넘어 매개변수를 여러 줄로 나눌 때 마지막에 `)`가 빠졌다. 1단계 빌드(`lib/com/message.c`)에서 컴파일 오류로 즉시 드러났고, 해당 파일 10개를 백업으로 복원(복원 후 `git status`가 시작 상태와 동일함을 확인)한 뒤 도구를 고쳐 1단계를 다시 실행했다. 이후 8단계 모두 오류 없이 통과했다.
- 비교 도구 보강 1건: 2절의 `PROTO` 분류와 주소 정규화는 4단계의 `acon_parse.o` 차이를 분석한 뒤 추가했다.

## 8. 빈 괄호 `f()` 선언 15곳 수정 (추가 작업)

C23에서는 빈 괄호 `f()`가 `f(void)`로 해석된다. K&R 변환 뒤 전체 스캔(`-Wstrict-prototypes`)에서 15곳(중복 제거)이 남아 있었고, 이 중 인자를 넘기는 호출이 있는 곳이 있어 C23 모드에서 실제 오류가 났다.

### 8.1 수정 내용

| # | 위치(변경 전 줄) | 종류 | 변경 전 | 변경 후 |
|---:|---|---|---|---|
| 1~6 | `include/pdu/var_struct.h` 34, 50, 59, 68, 77, 86 | 구조체 멤버 `findVar` (6개 구조체) | `u_char *(*findVar)();` | `pdu_find_var_t findVar;` |
| 7 | `include/pdu/pdu_impl.h` 587 | `getStatPtr()` 선언의 `write_method` | `int (**write_method)()` | `pdu_write_method_t *write_method` |
| 8 | `lib/pdu/pdu_tree.c` 94 | `getStatPtr()` 정의의 `write_method` | `int (**write_method)()` | `pdu_write_method_t *write_method` |

위 15곳 외에 같은 타입을 쓰는 곳을 함께 고쳤다(경고 대상은 아니지만 타입 일치에 필요).

- 신규 파일 `include/pdu/pdu_callback.h`: `pdu_write_method_t`, `pdu_find_var_t` 타입 정의. `var_struct.h`와 `pdu_impl.h`가 모두 include한다(두 헤더의 include 순서가 파일마다 달라서 별도 헤더로 분리했고 include 가드가 있다).
- `lib/pdu/module_vars.c`: 콜백 `var_notdefined()`, `var_system()`, `var_comm()`의 매개변수 `int (**write_method)`를 `pdu_write_method_t *write_method`로 바꾸고, `#ifdef _VME` 안의 `extern` 선언 5개도 같은 타입으로 맞췄다. 함수 본문은 그대로이다.
- `lib/pdu/pdu_tree.c`의 `#ifdef _WIN32` 안 `pdu_set_callback_grp()` 변형(509줄)도 같은 타입으로 맞췄다. 이 줄은 Linux 빌드에서 컴파일되지 않는다.

### 8.2 수정 근거 (소스에서 확인한 사실)

- `lib/pdu/pdu_tree.c:183`에서 `(*(vp->findVar))(cvp, name, namelen, exact, len, vnode, write_method)`로 인자 7개를 넘겨 호출한다. 선언이 `()`이면 C23에서 인자 0개 함수이므로 오류이다. 새 `pdu_find_var_t`는 이 호출의 인자 타입과 `module_vars.c`의 `var_system()` 등 콜백 정의의 시그니처에 맞춘 것이다.
- `module_vars.c`의 변수 테이블(`struct variable2 xxx_variables[]`)이 `findVar` 자리에 `var_system`, `var_notdefined`를 대입한다. 새 타입과 시그니처가 같아 대입이 그대로 컴파일된다.
- `write_method`는 콜백이 `*write_method = NULL;`로 비우는 것(`module_vars.c`)과 주소를 넘기는 것(`pdu_parse.c`) 외에 읽거나 호출하는 곳이 없다. 그래서 `pdu_write_method_t`는 `int (*)(void)`로 정의했고, 쓰기 함수를 실제로 연결할 때 시그니처를 정의해야 한다고 헤더 주석에 적었다.
- 수정 전에는 콜백 정의 쪽이 `int (**write_method)`(= `int **`)이고 호출 쪽이 `int (**write_method)()`(함수 포인터의 포인터)로 서로 타입이 달랐다. 호출이 인자 정보 없이 컴파일되어 드러나지 않았던 불일치이다. 이번에 한 타입으로 통일했다. 두 타입 모두 포인터라 크기·표현이 같고 대입하는 값은 `NULL`뿐이라 실행 동작은 달라지지 않는다.
- `setCurNo`는 `acon_server.c:32`의 선언 한 줄뿐이고 소스 전체에서 정의도 호출도 없다.
- `errno` 두 줄: 해당 파일에서 `<errno.h>`의 `errno` 매크로가 이미 적용되어 있어, 이 줄은 `int (*__errno_location ());`라는 함수 선언으로 바뀌어 아무 일도 하지 않았다. 삭제 후에도 오브젝트가 같다(8.3).

### 9.5 검토가 필요한 항목 (로직에 영향 가능)

- **`src/acon_agent/socket.c:192`** `if (ntohl(addr) == 0x0A000001)`: `addr`은 `unsigned int *`인데 값(`*addr`)이 아니라 포인터 자체를 `ntohl`에 넘기고 있어, 이 조건은 사실상 항상 거짓이다. 의도는 "인터페이스 IP가 10.0.0.1이면 `*addr`, `*mask`를 0으로 초기화"로 보인다. 이 의도대로 `ntohl(*addr)`로 고치면 10.0.0.1일 때 동작이 달라지므로 고치지 않고 기존 동작을 유지했다. 판단이 필요하다.
- **`gets` → `fgets`** (`emon`, `util/config`): 입력이 버퍼 길이(81바이트, 80바이트)보다 길면 `gets`는 버퍼를 넘쳐 쓰고, `fgets`는 잘라서 읽으며 남은 입력이 다음 입력으로 넘어간다. 두 프로그램은 운영자가 직접 쓰는 대화형 도구이다.

## 11. 확인하지 못한 것 / 사용자 확인이 필요한 것

- **장치 빌드**: 장치(Raspberry Pi 3, Debian, gcc 14.2, armv7l)에서의 `make clean all` 결과는 확인하지 못했다. 성공 기준은 `BUILD_EXIT=0`, `error:` 0건이며, 경고 건수는 변환 전 장치 빌드와 같아야 한다(장치 빌드 옵션에도 `-Wold-style-definition`이 없으므로 이 환경의 514→514와 같은 결과를 기대하지만 장치에서 확인한 값은 아니다). 이 환경의 경고 건수(514건)는 x86_64 기준이라 장치 기준값(스킬 문서 405건 이하, 정리 후 측정 446건)과 직접 비교할 수 없다.
- **pytest 신·구 DP 비교 테스트**: 실행하지 않았다.
- **armv7l 코드 생성**: 오브젝트 비교는 x86_64에서만 했다.
- **gcc 15·16의 x86_64 빌드는 확인했다**(9.2절). 장치용 armv7l 크로스 빌드는 하지 못했다. 32비트에서만 나오는 진단이 있는지는 알 수 없다.
- **`-Wno-error=...` 옵션 제거**: 최종 소스는 이 옵션 없이도 gcc 15·16(x86_64)에서 오류가 없다. 옵션은 그대로 두었고, 장치 빌드로 확인한 뒤 제거할지 결정이 필요하다.
- **`socket.c:192`의 `ntohl(addr)` 의도**(9.5절): 확인이 필요하다.
- **`write_method` 시그니처**: 이 저장소에서 호출하는 곳이 없어 `int (*)(void)`로 정의했다. 쓰기 함수를 실제로 연결할 계획이 있다면 시그니처를 정해야 한다.
