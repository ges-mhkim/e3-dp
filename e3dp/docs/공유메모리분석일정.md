# E3-DP 공유 메모리 분석 일정

> 기준 문서: [공유메모리구조.md](공유메모리구조.md), [메모리·파일 소스 연계표](메모리_파일_소스연계.md)
> 분석 대상: `e3dp.2.1` 소스의 SysV 공유 메모리 19개 세그먼트와 파일 공유 메모리 1개(`alarm.db`).
> 일정 단위: 시작일·종료일을 지정하지 않는 **누적 실투입일(인일)**. 아래 일정은 분석 공수의 초기 추정이며 실적이 아니다.

## 0. 현재 진행 상황과 첫 분석 대상

**이번 주는 전체 공유 메모리 구조 파악과 분석 계획 수립을 진행 중이며, 첫 세그먼트 상세 분석 대상은 `netconfig`로 한다.**

| 구분 | 내용 | 상태 |
|---|---|---|
| 이번 주 작업 | 전체 구조·영역별 규모·프로그램 연결 관계 파악, 분석 범위·방법·투입일 계획 정리 | 진행 중 (D1 범위) |
| 첫 상세 분석 | `netconfig`의 구조체 멤버, 설정 입력, 초기화·쓰기·읽기, 사용법 추적 | 예정 (D2 범위) |
| 이후 순서 | `shard_m`·`Proc` → `DrDB` → 나머지 영역 → 통합 검토 | 예정 |

이번 주 작업도 분석 계획의 D1 공수에 포함한다. 다만 주 20%는 배정 기준이므로, 이번 주를 자동으로 1투입일 완료로 처리하지 않는다. 실제 작업시간과 D1 완료 여부를 확인한 뒤 실적에 반영한다. 시작일과 종료일은 지정하지 않으며 이후 일정도 누적 투입일로 관리한다.

### 첫 상세 분석: `netconfig` 작업 계획

`netconfig`를 첫 사례로 분석하면서 변수 추적표의 작성 수준을 정하고, 같은 양식을 이후 세그먼트에 적용한다. 아래 항목은 예정 작업이며 분석 완료 결과가 아니다.

| 순서 | 분석 항목 | 확인·작성할 내용 |
|---|---|---|
| 1 | 영역·변수 정의 | `NetworkConfigRec`의 전체 멤버, 타입·배열 길이·크기, 공유 메모리 키와 대표 포인터 정리 |
| 2 | 생성·연결 | `CreateSharedMemory()`와 각 프로그램의 attach 경로, 생성·연결 실패 처리 확인 |
| 3 | 입력·초기화·쓰기 | `nelite.conf`의 설정 항목이 `main_server`를 통해 어떤 멤버에 기록되는지 추적. 누락값·초기값·재기동 시 동작 확인 |
| 4 | 읽기·출력 | 멤버별 참조 프로그램·함수, 주소·식별 정보 등 사용 목적과 후속 처리 추적. attach만 하는 프로그램 구분 |
| 5 | 사용법·변경 반영 | 기동 순서, 설정 변경 반영 시점, 다른 공유 영역으로 복사되는 값과 소비 시점 확인 |
| 6 | 결과 검토 | 전체 멤버 대비 누락 점검, 변수 사전·R/W 표·입출력 흐름 작성, 미확인 항목 기록 |

산출물은 **`netconfig` 변수 사전, 멤버별 입출력 추적표, 설정 파일에서 소비 프로그램까지의 흐름, 사용법·미확인 항목**이다. D2 완료 시 첫 사례의 실제 공수를 확인하고 이후 영역의 예상 공수를 보정한다.

## 1. 권장 공수와 산정 전제

**기본 분석 15일 + 예비 공수 3일 = 총 18투입일**을 권장한다. 현재 주당 20% 투입을 주 1일로 환산하면 기본 분석은 약 15주, 예비 공수까지 사용하면 약 18주가 걸린다. 투입률이 달라져도 작업 순서는 유지하고 남은 투입일을 다시 계산한다.

| 구분 | 예상 투입일 | 포함 범위 |
|---|---:|---|
| 기본 분석 | 15일 | 세그먼트·변수 목록 검증, 필드별 입출력 추적, 사용법·상태 전이 정리, 교차 검토 |
| 예비 공수 | 3일 | 간접 쓰기·호출 경로 추가 확인, 조건부 컴파일 차이, 미확인 항목 재조사 |
| 계획 공수 | **18일** | 기본 분석 + 필요 시 사용하는 예비 공수 |

- **1투입일 = 분석 담당자 1명의 순수 작업 8시간**으로 가정한다. 실제 조직의 1일 기준이 다르면 시간 환산 기준을 바꾼다. 4시간 작업은 0.5일로 누적한다.
- 기존 문서의 구조·크기·attach 표를 재사용하고, 이번 작업에서는 **내부 변수별 근거와 호출 경로를 보강**한다. 기존 문서 작성 시간을 자동으로 소급 집계하지 않으며, 이번 주에 진행 중인 구조 파악·계획 수립은 D1 작업으로 실제 시간을 기록한다.
- 기본 범위는 소스 기반 분석이다. 배포 바이너리 대조, 운영 장비 실측, 실행 재현 시험, 코드 수정은 별도 공수로 산정한다.
- 웹 CGI·일반 유틸리티는 기본 분석의 프로그램 집계 범위에서 제외한다. 다만 공통 라이브러리나 헬퍼를 통해 대상 영역에 접근하는 경로는 추적한다.
- 변수는 대표 포인터 20개에 그치지 않고 **구조체 내부의 명명된 멤버 경로**까지 분석한다. 동일 구조의 배열 원소는 `lport[i].value`처럼 묶고, 인덱스 계산·유효 범위·예외 사용은 별도로 기록한다.
- 메모리 크기만으로 공수를 나누지 않는다. 연결 프로그램 수, 필드 수, 다중 쓰기, 상태 전이, 간접 접근의 복잡도를 기준으로 배분한다. `DrDB`는 이를 고려해 5일을 배정한다.

## 2. 분석 순서와 방법

세그먼트별로 아래 순서를 반복한다. **정의 → 생성·연결 → 초기화 → 쓰기 → 읽기 → 사용 조건·수명 → 예외**를 한 흐름으로 설명할 수 있게 만드는 것이 목표이다.

| 단계 | 확인할 내용 | 기록할 근거 |
|---|---|---|
| ① 영역 식별 | 키/파일 경로, 대표 변수, 구조체, 크기·패킹·ABI, 연결 프로그램 | 헤더 정의, 생성·attach·mmap 함수 |
| ② 변수 목록 | 멤버명, 타입, 배열 길이, 의미, 단위, 허용값, 인덱스 범위 | 구조체 선언, 상수·열거형, 사용 코드 |
| ③ 초기화·쓰기 추적 | 누가 언제 어떤 조건과 원본 데이터로 값을 기록하는가 | 함수·호출 경로, 대입, 증감, 초기화 함수 |
| ④ 읽기·출력 추적 | 누가 어떤 조건으로 읽고 어떤 판단·응답·전송에 쓰는가 | 분기, 함수 인자, 메시지 인코딩·전송 경로 |
| ⑤ 사용법 정리 | 기동 순서, 폴링 주기, 상태 전이, 재시작·다운로드·삭제 동작 | 호출 순서, 플래그 검사, 생성·해제·재생성 경로 |
| ⑥ 예외·정합성 검토 | attach 없는 사용, 미사용 필드, 다중 쓰기, 범위 초과, ABI 차이 | 활성/비활성 코드 구분, 근거 위치, 영향 조건 |

입력·출력은 외부 I/O뿐 아니라 **공유 변수 기준의 쓰기(W)·읽기(R)**를 뜻한다. 가능하면 `입력 원천 → 쓰기 함수 → 공유 변수 → 읽기 함수 → 결과/외부 출력`까지 연결한다. 초기화 쓰기와 정상 운영 쓰기, attach와 실제 접근은 구분한다.

검색은 선언과 참조 수집에 사용하고, 실제 접근 여부는 전처리 결과와 호출부로 확인한다. `memcpy`, `memset`, 포인터 별칭, 구조체 전체 복사, 헬퍼 함수에 의한 간접 쓰기도 포함한다. 근거가 없는 의미나 단위는 추정으로 확정하지 않고 미확인으로 남긴다.

## 3. 일 단위 작업 계획

아래의 D1~D15는 달력의 연속 날짜가 아니라 **실제 투입을 누적한 작업 순서**이다. 하루 작업을 여러 주에 나누어 수행해도 된다.

| 누적 투입일 | 대상 | 당일 작업 | 완료 산출물 |
|---|---|---|---|
| D1 | 전체 구조·분석 계획 (이번 주 진행 중) | 소스 버전/빌드 조건 고정, 20개 영역·연계 프로그램 목록 대조, 변수 추적 양식과 미확인 목록 작성 | 기준 목록, 집계 규칙, 추적표 양식 |
| D2 | `netconfig` (첫 상세 분석) | 설정 파일 적재부터 각 소비 프로그램까지 멤버별 추적, 변경 반영 시점 확인 | 설정 변수 사전·R/W 표 |
| D3 | `shard_m`, `Proc` | 카운터·종료·버전 필드, 감시·재기동 경로와 주기, 예약 슬롯 분석 | 관리 변수 사전·감시 시나리오 |
| D4 | `DrDB` 헤더 | 구성 개수, 다운로드·제어·재초기화 플래그, 초기화 범위와 상태 전이 추적 | 헤더 변수 사전·상태 전이표 |
| D5 | `DrDB.comp[]`, `point[]` | 구성 다운로드·복원, 물리/논리 연결 및 인덱스 사용 조건 추적 | 구성·포인트 매핑표 |
| D6 | `DrDB.lport[]` 정의·설정 | 식별자, 포트 유형, 한계값·마스크·설정 변경 경로 추적 | 논리포트 설정 변수 사전 |
| D7 | `DrDB.lport[]` 값·통신·제어 | 현재값, 통신상태, 제어 요청의 생산·소비 경로와 다중 쓰기 추적 | 수집·제어 R/W 경로표 |
| D8 | `DrDB.lport[]` 경보·피크·시간 | 경보 상태·이전값·피크·시각 필드, 미사용 필드까지 대조 | 논리포트 변수 추적표 완성 |
| D9 | `DrSI`, `raw_idx` | 장비 구성·통신상태, 인덱스 생성·조회, 배열 범위와 재구성 시점 추적 | 장비 상태·인덱스 사용법 |
| D10 | `DrPCB`, `PeakDB` | 이력 기록·조회·전송·응답 후 삭제, 버퍼 인덱스·경계 동작 추적 | 정시·피크 버퍼 수명 및 R/W 표 |
| D11 | `DcdsDB`, `UpsDB` | 이력 생성·소비, attach 누락과 호출 조건, 버퍼 상태 필드 추적 | DC·UPS 버퍼 사용법·예외 목록 |
| D12 | 정전·발전기 플래그 9개 | 개별 값 의미, 판정 조건, 지연 카운트, 참조 프로그램 구분 | 플래그별 상태 전이·사용법 |
| D13 | `DR_ACB` / `alarm.db` | 파일 생성·매핑, 블록 멤버, 적재·전송·해제, 재기동 초기화, 32/64비트 차이 추적 | 파일 공유 메모리 변수 사전·수명 |
| D14 | 프로그램 간 통합 흐름 | 기동, 구성 다운로드, 계측·경보, 제어, 이력 전송, 재기동 흐름 교차 확인 | 시나리오별 변수 입출력 흐름도 |
| D15 | 최종 검토·문서 반영 | 선언 대비 추적 누락 점검, 통계·R/W 표 정합성 확인, 미확인 항목과 결론 정리 | 분석 문서·추적표·후속 과제 |
| D16~D18 | 예비 공수 | 남은 간접 접근·빌드 분기·미확인 의미 재조사, 검토 보완 | 추가 근거·미확인 항목 처리 결과 |

`DrDB` 작업은 D4~D8의 5일이다. 1 B 플래그 9개는 서로 연결된 판정 로직으로 묶어 하루에 분석한다. 영역을 단순히 하나당 하루로 계산하지 않는다.

## 4. 산출물 양식과 완료 기준

분석 결과는 [공유메모리구조.md](공유메모리구조.md)에 요약을 반영하고, 상세 변수 추적표는 분량에 따라 별도 문서로 분리해 연결한다. 아래는 작성 양식이며 실제 분석 결과는 아니다.

| 영역 | 변수/멤버 경로 | 타입·용량 | 의미·단위·허용값 | 초기화 | 입력 원천·W 프로그램/함수 | R 프로그램/함수·출력 용도 | 실행 조건·주기 | 소스 근거 | 확인 상태 |
|---|---|---|---|---|---|---|---|---|---|
| 대상 영역 | `구조체.배열[i].멤버` | 선언 기준 | 확인값 또는 미확인 | 시점·값 | 원천 → 쓰기 경로 | 읽기 경로 → 결과 | 조건·주기 | 파일·함수·행/소스 버전 | 확인 / 추정 / 미확인 / 비활성 |

영역별 완료 기준은 다음과 같다.

- 구조체의 모든 명명된 멤버가 추적표에 있고, 배열은 대표 경로와 인덱스 규칙으로 설명되어 있다.
- 초기화·정상 쓰기·읽기의 주체와 조건이 소스 근거에 연결되어 있다. 접근이 없는 필드도 조사 범위와 함께 표시한다.
- 활성 코드와 주석·`#if 0` 코드를 구분하고, attach만 하는 경우와 attach 없이 참조하는 경우를 구분한다.
- 생성부터 재시작·초기화·해제까지 사용법을 설명하고, 다중 쓰기나 순서 의존성이 있으면 조건과 영향을 기록한다.
- 미확인 항목은 원인·영향·추가 확인 방법을 적는다. 핵심 동작을 설명하지 못하는 항목이 남으면 해당 영역은 진행 중으로 두고, 소스만으로 확정할 수 없는 사항은 후속 검증 대상으로 명시한다.

중간 점검은 **D2(첫 `netconfig` 분석·양식 검토), D3(추적 양식·실제 분석 속도), D8(핵심 DB), D13(20개 영역), D15(통합 검토)**에 수행한다. D2의 실제 공수를 확인하고 D3와 D8에서 남은 공수를 재산정한다.

## 5. 투입량 변경과 실적 관리

현재 가정은 주 5일 중 20%인 **주 1투입일**이다. 주별 배정이 바뀌면 실제 작업시간을 누적하고, 남은 작업의 예상 공수를 갱신한다.

| 주당 평균 투입률 | 주당 투입일 | 기본 15일 소요 주수 | 예비 포함 18일 소요 주수 |
|---|---:|---:|---:|
| 10% | 0.5일 | 30주 | 36주 |
| 20% (현재 가정) | 1일 | 15주 | 18주 |
| 40% | 2일 | 7.5주 | 9주 |
| 60% | 3일 | 5주 | 6주 |
| 100% | 5일 | 3주 | 3.6주 |

위 주수는 일정한 평균 투입을 가정한 참고값이다. 실제 주별 배정량이 정해지면 남은 예상 공수를 채울 때까지 주별 투입일을 누적한다. 예를 들어 0.5일, 1.5일, 1일을 작업했다면 달력상 3주 동안 **3투입일**을 사용한 것이다.

- `실제 누적 투입일 = 실제 누적 분석시간 ÷ 8시간`
- `갱신 총 예상 공수 = 실제 누적 투입일 + 남은 기본 작업 예상 공수 + 남은 예비 공수`
- `참고 잔여 주수 = (남은 기본 작업 예상 공수 + 남은 예비 공수) ÷ 향후 주당 평균 투입일`

실제 투입일과 작업 완료율은 별도로 관리한다. 3일을 사용했어도 D3 범위가 끝나지 않았으면 진척을 D3 완료로 표시하지 않는다. 예비 공수를 사용했을 때는 사용 사유와 남은 예비량을 기록하고, 기본 작업의 초과분과 중복 계산하지 않는다.

| 작업 회차 | 실제 투입시간 | 실제 투입일 | 누적 투입일 | 수행 대상·완료 범위 | 남은 기본 작업 예상일 | 남은 예비일 | 이슈·다음 작업 |
|---|---:|---:|---:|---|---:|---:|---|
| 이번 주 (진행 중) | 미입력 | 미산정 | 미산정 | D1: 전체 구조 파악·분석 계획 수립 진행 중 | D1 잔여 + D2~D15의 14일 | 3 | D1 정리 후 첫 상세 분석은 `netconfig` |

이번 주 실제 투입시간이 아직 입력되지 않았으므로 잔여 공수를 확정하지 않는다. D1이 계획대로 1투입일에 완료되면 이후 기본 작업 14일과 예비 3일, 합계 **17투입일**이 남는다.

## 6. 계획에 대한 의견

**세그먼트 단위로 시작해 내부 변수의 입력·출력과 사용법까지 내려가는 방식이 적절하다.** 기존 문서에 이미 영역 구조와 연결 관계가 있으므로, 이번 분석의 가치는 필드별 의미와 근거를 채우고 프로그램 사이의 실제 동작 순서를 연결하는 데 있다.

이번 주 구조 파악·계획 수립을 포함해 18투입일을 계획값으로 두고, `netconfig`부터 상세 분석을 시작한다. D2에서 첫 분석 결과를 검토하고 D3에서 추적표 작성 속도를 확인하고 D8에서 가장 복잡한 `DrDB` 분석 결과를 기준으로 남은 공수를 조정하는 것을 권장한다. 운영 실측까지 필요해지면 소스 분석의 완료 기준과 분리해 추가 일정으로 잡는다.
